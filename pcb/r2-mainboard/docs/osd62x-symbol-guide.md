# `OSD6254-1G-IPM` — a guide to building the schematic symbol

Written **2026-09-11** from `datasheets/SiC OSD62x-PM/`, for Phase 3 of `NOTES-R2-osd62x-plan.md`.
Tags as in that plan: **[B]** checked in this repo on this date · **[W]** vendor fact as reported by
the web handoff, not re-read here · **[I]** inferred — check before relying on it.

> **Built 2026-09-11:** `Reflow:OSD6254-1G-IPM` in `library/Reflow.kicad_sym`, generated by
> `tools/gen_osd62x_symbol.py` to the rules below. It replaced SamacSys's single-unit import in place,
> keeping the name and every pin number. Each unit is top-aligned, so one Reference/Value position
> above the body clears all eleven. The footprint is SamacSys's `Reflow:BGA500C50P28X18_1400X900X130`
> (`libraries.md` §6).

---

## 0. The short version

1. **Don't type 500 pins by hand.** KiCad 10.0.4's Pin Table exports CSV but has no import (checked
   in `_eeschema.kiface`), and `tools/gen_som_symbol.py`'s header already says why: at this size,
   transcription puts silent errors into a part whose every pin is invisible to ERC. Generate the
   symbol from `osd62x_pm_pinout.json`. If you draw it anyway, run the §7 checks on the result.
2. **The pin table is verified three ways** [B]. The datasheet's ball map and its ball-description
   tables agree on all 500 balls, and so does Octavo's own Eagle library inside the BRK design files:
   407 identical names, and the other 93 are NC balls it numbers `NC_01…` or calls `AM62X_DNU…`.
   **No signal disagrees.**
3. **Pin number = ball name** (`A2` … `V27`). **Pin name = the datasheet's Pin Name, verbatim.**
4. **Eleven units, by function**, so the 22 DPI pins form one unit that sits on `dpi_in`.
5. **Never hide a pin.** KiCad 10 connects a hidden power pin to a net named after the pin, so a
   hidden `VSS` would silently create a net `VSS` beside `GND`.
6. **`NC` and reserved balls are `no_connect`**, so ERC objects if anything is ever wired to them.

## 2. The package, in numbers [B]

- **9 × 14 mm, 0.5 mm pitch**; 1.3 mm tall [W].
- **18 rows `A`–`V` × 28 columns.** The row letters skip `I`, `O`, `Q` and `S`, and the four corners
  `A1`, `A28`, `V1` and `V28` are depopulated: 18 × 28 − 4 = **500**.
  ⚠ Datasheet §8 says "14 x 28". That is wrong — 9 mm at 0.5 mm pitch is 18 rows, and the parse finds
  exactly 500 balls on the 18-row grid.
- **What the 500 are:** 104 `VSS`, 93 `NC`, 10 reserved, 72 supply balls (40 core/DDR, 32 IO/analog),
  and 221 signals.

## 3. Pins

### 3.1 Number = the ball name

`A2`, `B14`, `V27`… exactly as the ball map prints them, and exactly as the footprint names its pads.
That is how the `BTH-060` symbols were done (`som.md` §10.2): no mapping table exists, so none can be
wrong.

⚠ **Ball names look like reference designators** — `C1`, `D2`, `R25`, `U11`. `CLAUDE.md` and
`layout.md` §9.5 forbid bare-string substitution for exactly this reason. Never search-and-replace
across a file that contains this symbol.

### 3.2 Name = the datasheet's Pin Name, verbatim

Take the name from Tables 5-6 and 5-7, character for character: `MCU_PORZ`, `GPMC0_AD8`,
`AM62X_RSVD3`, `DDR_RSVD0`, and plain **`NC`** for all 93 NC balls. Two reasons. The §7 check compares
names mechanically against the JSON. And Octavo chose these names so they cross-reference to TI's
AM62x documents, which is where every function lookup will go.

- **Don't use PHYTEC's names.** They carry an `X_` prefix and a few typos (`som.md` §1).
- **Don't use Octavo's Eagle names.** `NC_01`…`NC_77` and `AM62X_DNU0`…`15` would make the symbol
  disagree with the datasheet, which is the binding document.
- ⚠ **The datasheet's "AM62x Pin No." column is the AMC package.** PHYTEC's `som_pinout.json` records
  the **ALW** package — `VOUT0_DATA13` is `V21` in one and `AA24` in the other. **Never compare ball
  numbers across the two.** R2's nets carry over by AM62x *signal name* (§6).

### 3.3 Electrical types

Octavo's Eagle library is no help here: every one of its 500 pins is direction `io`. So the types
are ours. They follow `gen_som_symbol.py`'s `TYPE_MAP` wherever the same situation came up.

| Pins | KiCad type | Why |
| --- | --- | --- |
| `VSS` ×104 | `power_in` | the house convention — the FPGA's 26 GND pins and `gen_som_symbol.py`'s GND rows |
| every `VDD*`, `VDDA*`, `VDDS*`, `VDDSHV*`, `DDR_VPP` | `power_in` | ERC then catches a rail nothing drives |
| `VPP` | `power_in`, **plus a no-connect flag on the sheet** | must be 0 V in normal use and "can be left unconnected" (Table 7-4 note 8); typing it `no_connect` would hide it if OTP programming is ever wanted |
| `VMON_VSYS`, `VMON_1P8_SOC`, `VMON_3P3_SOC` | `input` | sense inputs — the same call `gen_som_symbol.py` made for VBUS sensing |
| `USB0_VBUS`, `USB1_VBUS` | `input` | likewise; both need an external divider (Table 7-2 note 6) |
| `MCU_PORZ`, `MCU_RESETZ`, `RESET_REQZ`, `EXTINTN` | `input` [I] | |
| `PORZ_OUT`, `RESETSTATZ`, `MCU_RESETSTATZ`, `PMIC_LPM_EN0` | `output` [I] | |
| `MCU_OSC0_XI`, `WKUP_LFOSC0_XI` / `…_XO` | `input` / `output` [I] | `passive` for all four is also fine |
| `TCK`, `TDI`, `TMS`, `TRSTN` / `TDO` | `input` / `output` [I] | |
| `NC` ×93, `AM62X_RSVD0`…`8`, `DDR_RSVD0` | `no_connect` | §5.2–5.3: "must remain unconnected". ERC then errors if anything touches them |
| **everything else** — `EMU0/1`, `MCU_ERRORN`, all peripheral balls | `bidirectional` | a pin-muxed SoC. Any fixed direction is wrong in some mux mode, and wrong directions cause false ERC conflicts |

The [I] rows follow AM62x naming conventions. Confirm them against the signal descriptions in
`SPRSP58` once it is in the repo (plan task E2).

### 3.4 Never hide a pin — and don't stack them either

KiCad 10.0.4's own ERC text, from `_eeschema.kiface`: *"Hidden power pins will drive their pin names
on to any connected nets."* A hidden `VSS` pin would create a net named **`VSS`**, separate from
`GND`. That is a split ground that ERC reports as clean.

Stacking — several visible pins at one position — is legal in KiCad, but it isn't house style. The
repo's FPGA symbol draws all 26 of its GND pins visibly, one position each. Do the same: the `GND`
unit becomes 52 pins down each side.

### 3.5 Alternate pin functions — optional

KiCad 10 supports per-pin alternate names. It does not allow them on symbols with more than one body
style, so keep one body style. Nothing in the repo uses alternates yet. They help on the few balls
whose R2 function differs from their name:

| Ball | Name | Alternate(s) | Source |
| --- | --- | --- | --- |
| `L27` / `L28` | `GPMC0_AD8` / `GPMC0_AD9` | `VOUT0_DATA16` / `VOUT0_DATA17` (R2's `DPI_R6`/`R7`), `BOOTMODE_8` / `BOOTMODE_9` | `som.md` §2, from PHYTEC Table 31 |
| `E2` / `E1` | `MCU_MCAN0_TX` / `MCU_MCAN0_RX` | `MCU_GPIO0_13` (`SOM_IRQ#`) / `MCU_GPIO0_14` (`SOM_WAKE#`) | `som.md` §5.1, from `SPRSP58C` mux mode 7 |
| the other 14 `GPMC0_ADn` | `GPMC0_ADn` | `BOOTMODE_n` | PHYTEC's pin names, all 16 [B] |

Alternates change no connectivity — the net labels already carry the meaning — so skip them if they
get in the way. If they're used, re-check every alternate name against `SPRSP58` when it arrives.

**Octavo's own split**, for comparison: 13 gates — `PWR-IN` 51, `PWR-IO` 21, `VSS` 104, `WKUP` 9,
`MCU` 21, `CSI` 10, `MPU1` 106, `MPU2` 55, `USB` 8, `EMU-MISC` 12, `RSVD` 10, `DNU` 16, `NC` 77. It
puts the video pins in a 55-pin gate together with OLDI and OSPI, which is exactly what R2 can't use:
`dpi_in` would inherit 33 pins it has nothing to do with.

**Place every unit.** KiCad's ERC can flag units left unplaced when they carry input or power pins
[I]. `UNUSED_HS` goes on `som` with an X on each pin; `NC_RSVD` needs nothing.

## 5. Drawing it

House style, from `gen_som_symbol.py` and the FPGA symbol:

- **Pin length 5.08 mm, pin text 1.27 mm, 2.54 mm grid**, one position per pin.
- **`VIDEO` in bus order, not ball order**, so the unit reads like the `DPI_*` nets it drives:
  `VOUT0_DATA0`…`5` (= `DPI_B2`…`B7`), `DATA6`…`11` (= `G2`…`G7`), `DATA12`…`15` then `GPMC0_AD8`,
  `GPMC0_AD9` (= `R2`…`R7`), then `PCLK`, `DE`, `HSYNC`, `VSYNC`.
- **Power units:** group each rail's balls together, and the core and DDR rails apart from the
  1.8 V / 3.3 V ones, so the decoupling sits next to the right pins (Table 4-3).
- **Properties:** Reference `U`. The part now lives on the new `sic` sheet, **page 15**, so by CLAUDE.md's
  rule it is **`U1500`** if every unit sits there — or **`U600`** if `VIDEO` goes on `dpi_in` (page 6),
  since a shared part takes its lowest page. That choice is the owner's. Value `OSD6254-1G-IPM`. Manufacturer `Octavo Systems`, MPN `OSD6254-1G-IPM`, no LCSC code
  (not stocked there). Datasheet: `datasheets/SiC OSD62x-PM/OSD62x-PM-Datasheet.pdf`. Footprint:
  `Reflow:BGA500C50P28X18_1400X900X130`.
- **Library:** `r2.kicad_sym` — `pcb_common` is never modified — with a row in `libraries.md` naming
  the generator and what it checked.

⚠ `DPI_R6`/`DPI_R7` are also `BOOTMODE_8/9`, which sit inside the **primary boot-mode field**
`BOOTMODE[9:3]` (`som.md` §2). Their strap resistors pick the boot device, and they have to overpower
the Spartan-6's `HSWAPEN` pull-ups on the same nets.

**E3 — "are all of R2's signals in rings 1–3?" No.** Nine sit in **ring 4**: `VOUT0_DATA1` (`N25`),
`VOUT0_DATA3` (`M25`), `VOUT0_DE` (`R25`), `VOUT0_HSYNC` (`P25`), `SPI0_CS0` (`D13`), `SPI0_D0`
(`D12`), `USB1_DRVVBUS` (`D19`), `MCU_PORZ` (`D6`) and `PMIC_LPM_EN0` (`D5`). None is deeper than
ring 4. So the escape does need the inner-ring case from the handoff's §4.1 — vias in ring 3 with a
trace passing between them. On six layers that trace can drop to `In3.Cu` or `B.Cu`.

## 7. Acceptance checks — whichever way the symbol is made

1. **500 pins.** The set of pin numbers equals the JSON's 500 balls, none twice.
2. **Every pin name equals the JSON name** for its ball.
3. **Every pin is in exactly one unit**, and `VIDEO` holds exactly the 22 balls in §6's DPI rows.
4. **Types as §3.3; no pin hidden.**
5. **Footprint:** 500 pads, named exactly as the pin numbers.
6. **After capture:** the netlist puts each R2 net on the ball §6 lists — a `check_osd62x.py` in the
   spirit of `check_ucf.py`.

Checks 1–5 are a short script over the `.kicad_sym` and the JSON; check 6 is the one that catches a
wrong wire.

## 8. Footprint notes, for when Phase 3 gets there

- **Pads named like the balls**, 500 of them, 0.5 mm pitch, corners empty.
- **Land size is a real choice.** The datasheet (§8.1.1) quotes IPC-7351A: for the 0.30 mm ball the
  nominal NSMD land is **0.25 mm**, with a range down to **0.20 mm**, and says Octavo's own footprints
  "generally use the minimum". **The BRK's footprint uses 0.25 mm round lands** [B]. For escape the
  difference is decisive: a 0.20 mm land leaves 0.30 mm between balls — room for one 0.10 mm trace
  at 0.10 mm clearance — while a 0.25 mm land leaves 0.25 mm, which doesn't fit it. Settle this with
  the fab (plan E7).
- **Outline and pin-1 marker** come from the mechanical drawing on datasheet p. 31. It is an image,
  so read the dimensions off the page.
- **Assembly:** MSL 4 — 72 h floor life after the bag is opened, bake 34 h at 125 °C otherwise
  (§8.4) [B]; ENIG for the small lands [W]. Put both on the fab order.

## 9. Errors and traps found in the vendor material

1. **§8 "14 x 28 Ball Grid Array"** — actually 18 × 28 (§2).
2. **Table 7-4 swaps its core-voltage labels.** The row headed "0.85V operation" carries
   0.715 / 0.75 / 0.79 V, and "0.75V operation" carries 0.81 / 0.85 / 0.895 V.
3. **`VDDS_DDR` maximum current:** Table 7-3 says **600 mA**; the handoff quoted 800 mA from the power
   app note. Re-read the app note (E1) before sizing the PMIC's BUCK3.
4. **The 16 NC balls that Octavo's library calls `AM62X_DNU0`…`15`** (`V18 U18 T18 T17 T16 T15 R18
   R17 R16 R15 M14 F15 F16 J2 M19 N19`) are AM62x "do not use" balls, wired to the die rather than
   floating. Both sources say leave them unconnected, so the symbol treats them like every other NC.
5. **§4 says "up to 16Gb (2GB)"**, but the ordering tables list only `1G`.
6. **The 2024 overview lists 0–85 °C `-BPM` and `-ES` parts** that the Rev. 2.0 ordering tables don't.
7. **The "AM62x Pin No." column is the AMC package** — the ALW/AMC trap in §3.2.
8. **The NC list has a missing comma** (`J4 J5`). Harmless; the parser handles it.
